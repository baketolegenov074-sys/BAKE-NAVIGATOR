# BAKE Navigator — подготовка Android-моста Valhalla

Статус: Kotlin-мост регистрируется в генерируемом Android MainActivity через build workflow. Flutter умеет импортировать отдельный Valhalla tile extract (.tar), инициализировать native engine и запрашивать маршрут A→B. При ошибке Valhalla или при наличии промежуточных остановок сохраняется переход на OSRM. В GitHub Actions run #208 (commit b8e9f84) шаги `flutter analyze` и `flutter build apk --release --target-platform android-arm64` завершились успешно; на момент последней проверки ещё выполнялась загрузка артефакта. Проверки на реальном телефоне нет.

## Цель первого этапа

Добавить локальный Android-модуль маршрутизации Valhalla так, чтобы Flutter-экран и существующий Dart-код продолжали получать маршрут в привычном OSRM-подобном JSON. На этом этапе нельзя удалять или менять текущий онлайн-маршрутизатор OSRM: он остаётся резервным вариантом, пока офлайн-движок не проверен.

## Проверенные Android-зависимости

По Maven Central и опубликованному README подтверждены координаты:

- `io.github.rallista:valhalla-mobile:0.6.6` — Android engine (версия, указанная в текущем `.github/workflows/build-android.yml`; публикация 0.6.6 подтверждена Maven Central).
- `io.github.rallista:valhalla-models:0.6.0` и `io.github.rallista:valhalla-models-config:0.6.0` — model/config artifacts, соответствующие engine 0.6.4 по опубликованным зависимостям.
- `com.stadiamaps:osrm-openapi:0.0.10` — OSRM response model; bridge сейчас возвращает raw JSON, но зависимость указана в README библиотеки для OSRM typed response.

Engine 0.6.6 публикуется с Kotlin stdlib 2.2.10. Шаблон Android для Flutter 3.27.4 использует Kotlin Gradle Plugin 1.8.22, Android Gradle Plugin 8.1.0 и Gradle 8.3. Kotlin 1.8.22 слишком стар для надёжной работы с metadata Kotlin 2.2.

По официальной таблице совместимости Kotlin Gradle Plugin 2.2.10 поддерживает Gradle 7.6.3–8.14 и AGP 7.3.1–8.10.0. Следовательно, текущие AGP 8.1.0 и Gradle 8.3 попадают в поддерживаемый диапазон; для подготовки достаточно поднять только Kotlin Gradle Plugin до 2.2.10, не меняя AGP, Gradle или Java 17. Источники: [Kotlin Gradle compatibility](https://kotlinlang.org/docs/gradle-configure-project.html), [Android Kotlin support](https://developer.android.com/build/kotlin-support).

В отдельной ветке `valhalla-bridge-prep` добавлен подготовительный шаг workflow: после `flutter create` он ищет ровно одну запись Kotlin Android plugin версии 1.8.22 и меняет её на 2.2.10. Если шаблон изменится и точное совпадение не будет найдено, шаг завершится ошибкой вместо незаметного изменения неизвестной конфигурации. Это пока не проверено запуском CI; workflow не запускался.

## Подготовленная настройка Kotlin

В `.github/workflows/build-android.yml` после генерации Android-платформы добавлен отдельный шаг, который обновляет только Kotlin Gradle Plugin с 1.8.22 до 2.2.10. Версии AGP 8.1.0, Gradle 8.3 и Java 17 оставлены без изменений. Скрипт проверяет точное совпадение шаблона и останавливается, если оно отсутствует или встречается не ровно один раз.

Это описание ранней подготовки. Позднее в GitHub Actions run #208 на commit b8e9f84 Flutter-анализ и release-сборка APK завершились успешно. Этот результат подтверждает компиляцию Android-моста в CI, но не работу маршрута на телефоне. Новые запуски workflow по-прежнему требуют отдельного разрешения.

## Что подтверждено документацией

- `Rallista/valhalla-mobile` предоставляет Android shared library и Kotlin API.
- На устройстве можно выполнять `route` по заранее подготовленным Valhalla tiles.
- Библиотека умеет выдавать ответ маршрута в OSRM-формате на Android.
- PBF напрямую не читается. Исходный OSM PBF необходимо заранее преобразовать в Valhalla tile set.
- Экземпляр `Valhalla` держит native actor и открытый tile extract; его нужно создавать один раз, переиспользовать для запросов и закрывать при завершении.
- Маршрутизацию нельзя выполнять на главном Android-потоке.
- В документации есть расхождение версий: README показывает более старые версии артефактов, страница API уже показывает 0.6.5, а опубликованный релиз/артефакт, который удалось подтвердить, — 0.6.4. В текущем workflow зафиксированы engine 0.6.6 и model artifacts 0.6.0; перед обновлением этих версий нужно повторно сверять их POM и совместимость.

## Предлагаемый контракт Flutter ↔ Android

Канал: `bake.navigator/valhalla`

Методы:
- `initialize`: принять путь к локальному Valhalla tile extract или каталогу tiles; вернуть готовность движка либо понятную ошибку.
- `route`: принять координаты начала и конца, параметры автомобильного профиля и запросить маршрут; вернуть JSON OSRM-формата, чтобы не переписывать существующий разбор маршрута в Dart.
- `dispose`: закрыть native actor и освободить tile extract.

Правила:
1. Один экземпляр движка на жизненный цикл сервиса, без пересоздания на каждый маршрут.
2. Все тяжёлые вызовы — вне UI-потока.
3. Ошибки отсутствующих/неподготовленных тайлов возвращать в Flutter как структурированную ошибку; не подменять её фиктивным маршрутом.
4. Существующий онлайн OSRM оставить резервным вариантом, пока офлайн-маршрут не прошёл проверку.
5. Не менять экран карты, голосовые подсказки, поиск адресов и текущую логику маршрута в рамках первого подключения.

## Особенность текущего CI

В репозитории нет постоянной папки `android/`: workflow генерирует Android-проект командой `flutter create` при каждой сборке. Поэтому Kotlin-файл моста, Gradle-зависимости и регистрацию MethodChannel потребуется добавлять в workflow после шага генерации Android-платформы. Сам workflow запускается при push только в `navigator-ui-work`; эта подготовительная ветка не входит в список триггеров.

## Подготовленный Kotlin source

Черновой класс находится в `android-bridge/ValhallaRoutingBridge.kt`. Он:

- регистрирует MethodChannel `bake.navigator/valhalla`;
- принимает путь к готовому Valhalla tile extract (`.tar`), открывает один долгоживущий engine;
- принимает координаты начала/конца и запрашивает автомобильный маршрут с `format: osrm`;
- возвращает Flutter исходный JSON-ответ, не меняя Dart-парсер;
- выполняет native routing в отдельном однопоточном executor и закрывает engine при dispose.

Workflow после `flutter create` копирует этот source в Android package и регистрирует `bake.navigator/valhalla` в `MainActivity`. Gradle dependency injection больше не требует заранее существующего блока `dependencies {}`: при необходимости workflow добавляет отдельный блок с синтаксисом выбранного Gradle DSL. Flutter-вызов канала, выбор архива и fallback на OSRM описаны в разделе «Текущее подключение Flutter» ниже. Для работы офлайн всё ещё требуется заранее преобразовать OSM PBF в Valhalla tile extract: PBF напрямую движок не читает.

## Текущее подключение Flutter

В `lib/main.dart` реализовано автоматическое подключение дорожного графа Шымкента:

- при открытии главного экрана приложение в фоне проверяет локальный архив;
- если архива ещё нет, загружает его из публичного GitHub Release по постоянной ссылке;
- сохраняет архив в приватном каталоге приложения, поэтому повторно скачивать его при каждом запуске не нужно;
- вызывает Kotlin `initialize`, затем строит контрольный маршрут «аэропорт Шымкента → центр»;
- сохраняет путь и показывает статус «Офлайн-маршрутизация Шымкента готова» только после успешной проверки;
- если загрузка или проверка не удалась, приложение продолжает использовать существующий интернет-маршрут OSRM;
- кнопка в настройках повторяет автоматическую проверку/загрузку и больше не открывает файловый менеджер для выбора `.tar`.

Офлайн-граф ограничен покрытием Шымкента и буферной области, заданной bbox в workflow. Маршруты с промежуточными остановками по-прежнему идут через OSRM. Реальная работа на Samsung ещё должна быть проверена; успешная серверная сборка и Flutter-анализ сами по себе этого не доказывают.

## Подготовка дорожного графа Шымкента

Добавлен отдельный workflow: `.github/workflows/build-shymkent-valhalla-tiles.yml`.

- Запускается вручную через `workflow_dispatch`, а также автоматически при изменении самого workflow в рабочей ветке.
- Скачивает актуальный Kazakhstan OSM PBF с Geofabrik и вырезает Шымкент с буфером: `69.35,42.12,69.90,42.53`.
- Использует официальный Docker image Valhalla для сборки routing graph, timezone/admin databases и индексированного tile extract.
- Проверяет наличие `index` и `.gph` в архиве и строит тестовый автомобильный маршрут.
- Загружает `shymkent-valhalla.tar`, README, SHA-256 и пример тестового маршрута как GitHub Actions artifact на 30 дней.
- Не собирает APK, не меняет релизы и не имеет триггера push.

Workflow подготовлен в репозитории, но **не запускался**. Поэтому готового архива пока нет. Запуск потребует отдельного подтверждения пользователя. После успешного запуска архив можно будет скачать из раздела Actions → Build Shymkent Valhalla Routing Tiles → Artifacts и импортировать в приложении через «Офлайн-маршрутизация».
