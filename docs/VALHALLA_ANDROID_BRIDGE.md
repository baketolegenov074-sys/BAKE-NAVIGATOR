# BAKE Navigator — подготовка Android-моста Valhalla

Статус: подготовительный документ. Рабочий Kotlin-код и Flutter MethodChannel пока не подключены.

## Цель первого этапа

Добавить локальный Android-модуль маршрутизации Valhalla так, чтобы Flutter-экран и существующий Dart-код продолжали получать маршрут в привычном OSRM-подобном JSON. На этом этапе нельзя удалять или менять текущий онлайн-маршрутизатор OSRM: он остаётся резервным вариантом, пока офлайн-движок не проверен.

## Что подтверждено документацией

- `Rallista/valhalla-mobile` предоставляет Android shared library и Kotlin API.
- На устройстве можно выполнять `route` по заранее подготовленным Valhalla tiles.
- Библиотека умеет выдавать ответ маршрута в OSRM-формате на Android.
- PBF напрямую не читается. Исходный OSM PBF необходимо заранее преобразовать в Valhalla tile set.
- Экземпляр `Valhalla` держит native actor и открытый tile extract; его нужно создавать один раз, переиспользовать для запросов и закрывать при завершении.
- Маршрутизацию нельзя выполнять на главном Android-потоке.
- В документации есть расхождение версий: README показывает более старые версии артефактов, страница API уже показывает 0.6.5, а опубликованный релиз/артефакт, который удалось подтвердить, — 0.6.4. Поэтому точные версии engine и model artifacts нужно сверить перед добавлением Gradle-зависимостей.

## Предлагаемый контракт Flutter ↔ Android

Канал: `bake.navigator/valhalla`

Методы:
- `initialize`: принять путь к локальному Valhalla tile extract или каталогу tiles; вернуть готовность движка либо понятную ошибку.
- `route`: принять координаты начала и конца, параметры автомобильного профиля и запросить маршрут; вернуть JSON OSRM-формата, чтобы не переписывать существующий разбор маршрута в Dart.
- `dispose`: закрыть native actor и освободить tile extract.

Правила:
1. Один экземпляр движка на жизненный цикл сервиса, без пересоздания на каждый маршрут.
2. Все тяжёлые вызовы — вне UI-потока.
3. Ошибки отсутствующих/неподготовленных тайлов возвращать в Flutter как структурированную ошибку; не подменять её фиктивным маршрутом.
4. Существующий онлайн OSRM оставить резервным вариантом, пока офлайн-маршрут не прошёл проверку.
5. Не менять экран карты, голосовые подсказки, поиск адресов и текущую логику маршрута в рамках первого подключения.

## Особенность текущего CI

В репозитории нет постоянной папки `android/`: workflow генерирует Android-проект командой `flutter create` при каждой сборке. Поэтому Kotlin-файл моста, Gradle-зависимости и регистрацию MethodChannel потребуется добавлять в workflow после шага генерации Android-платформы. Сам workflow запускается при push только в `navigator-ui-work`; эта подготовительная ветка не входит в список триггеров.

## Следующий безопасный шаг

До написания Kotlin-кода сверить точные Maven-координаты engine и model/config artifacts для одной совместимой версии, затем подготовить Kotlin bridge source и отдельные изменения workflow. Не запускать APK build и не переносить изменения в `navigator-ui-work` без отдельного разрешения владельца проекта.
